# CrossBorder Decision Lab 全仓审计与持续优化标准

标准版本：`CBDS-AUDIT-2026.07-v1`

适用对象：全仓发布、单域升级、ERDG 合同升级、跨域协议升级和 L4 生产成熟度评审

核心原则：**总分用于排序，硬门用于定性；证据不足不得用文字判断补分。**

## 1. 审计结论的五种状态

| 状态 | 使用条件 |
|---|---|
| `verified` | 审计人已在固定快照上执行并保存可复算证据 |
| `reported_not_reverified` | 引用其他审计执行结果，本轮未独立复跑 |
| `partial` | 仅覆盖声明范围的一部分 |
| `controlled_external_gate` | 需要授权真实数据、独立责任人或外部系统才能关闭 |
| `failed` | 已执行且未达到验收条件 |

禁止把 `reported_not_reverified` 写成 `verified`，禁止把测试存在写成测试通过，
禁止把 Golden、合成 fixture 或自动化断言写成真实经营有效。

## 2. 100 分审计模型

| 维度 | 分值 | 满分条件 |
|---|---:|---|
| A. 架构与治理一致性 | 12 | 架构注册表、主权、成熟度、合同版本和首页口径一致；planned/next_build fail closed |
| B. 可复现性与审计链 | 12 | 固定 commit、干净工作区、环境与依赖、命令、时间、退出码、原始日志和产物哈希齐全 |
| C. L1 结构完整性 | 8 | 目录、frontmatter、入口、链接、安装、导航、双语首页及打包验证全部通过 |
| D. L2 合同与确定性 | 12 | Schema、对象、证据、计算、状态、血缘、版本、幂等、精度、守恒和失败关闭均可机器验证 |
| E. L3 专家深度 | 16 | 每域有独有机制、计算、反事实、失败模式、动作、停止条件及独立失败断言；无关键词填充 |
| F. 跨域联动与主权 | 12 | handoff/cycle、owner、接收/拒绝/重算、冲突裁决、部分失败、禁止用途和回写血缘通过 |
| G. 场景、对抗与韧性 | 10 | 标准、边界、极端、恶意、漂移、多轮、容量、恢复和回滚覆盖，且守卫具有特异性 |
| H. 安全、发布与供应链 | 8 | 秘密、绝对路径、缓存、权限、依赖锁定、许可证、数据隐私、变更影响和回滚检查通过 |
| I. L4 真实经营有效性 | 10 | 每个拟宣称生产成熟的域满足授权、脱敏、异质、含结果与哈希的真实回放和独立复核 |
| **合计** | **100** | **同时满足硬门规则** |

### 2.1 分数解释

| 分数 | 评级 | 允许结论 |
|---:|---|---|
| 95—100 | A+ | 仅在全部硬门通过时可称 production-ready |
| 90—94 | A | 强受控试点；若 L4 未过，不得称生产成熟 |
| 80—89 | B | 可受控试点，存在明确整改项 |
| 70—79 | C | 仓库骨架可用，证据链或能力仍有重要缺口 |
| 60—69 | D | 仅限实验或内部开发 |
| <60 | F | 不得发布或对外作能力声明 |

分数不得跨成熟度层平均。即使总分达到 90，只要 L4 硬门未通过，最高成熟度仍是
`controlled pilot`。

## 3. 六个硬门

| 门 | 阻断条件 | 阻断范围 |
|---|---|---|
| G0 固定审计对象 | 无 commit SHA、工作区状态或审计产物哈希 | 阻断“可复现审计”结论 |
| G1 红线安全 | 秘密泄露、越权外写、伪造证据、非法状态跃迁、不可复算数字 | 阻断发布 |
| G2 L1/L2 基线 | 活跃域结构、合同、安装或共享校验失败 | 阻断 L3 与系统发布 |
| G3 主权与血缘 | 非 owner 改写正式结论、输入/输出哈希不一致、版本污染 | 阻断跨域发布 |
| G4 变更影响闭包 | authority、consumer、validator、test、evaluation 或 rollback 未闭包 | 阻断受影响发布 |
| G5 L4 真实性 | 无授权真实回放、无结果、无独立复核或用合成证据冒充 | 阻断 production-ready |

硬门失败时必须同时写明：事实、证据、影响范围、owner、整改动作、复验命令和退出条件。

## 5. 证据台账

每条结论必须对应一条证据记录：

| 字段 | 要求 |
|---|---|
| `claim_id` | 全局唯一 |
| `claim` | 单一、可证伪的结论 |
| `scope` | 系统、域、合同或场景 |
| `evidence_type` | source/test/log/golden/replay/external_review |
| `evidence_path` | 仓库相对路径或受控外部引用 |
| `command` | 可复跑命令；静态来源可写 `not_applicable` |
| `expected` / `actual` | 明确预期与实际结果 |
| `exit_code` | 执行证据必填 |
| `artifact_hash` | 关键输入、输出或日志哈希 |
| `status` | 五种审计状态之一 |
| `limitations` | 未覆盖边界和可能的替代解释 |

只给“ALL PASS”而没有命令、退出码和日志索引，最多获得该条证据分值的 50%。

## 6. 测试与专业深度最低要求

### 6.1 自动化测试

- 测试套件数量、测试文件数量、case 数量和 assertion 数量分别统计，不得混用。
- 必须由机器生成清单，禁止手工把“约 177”作为唯一总账。
- 每个关键守卫至少包含一个通过例和一个独立失败例。
- 对抗用例必须证明触发特定守卫，而不是因 JSON 无效等通用错误失败。
- 性能结果必须记录数据规模、硬阈值、机器环境、耗时、峰值内存和重复次数。

### 6.2 L3 专家深度

每个活跃域至少证明：

1. 本域主权和明确排除项；
2. 独有决策机制与确定性计算或判定；
3. 平台、国家、生命周期或经营模式差异；
4. 证据质量、未知项和反事实；
5. 至少三个本域特有失败模式；
6. 动作、停止、回滚、恢复或退出条件；
7. Golden、对抗和性质测试；
8. 对真实世界有效性的限制声明。

文件行数、关键词数量、模板复用率和测试通过本身都不能单独证明专业深度。

## 7. L4 生产成熟度标准

拟申请 L4 的每个域必须单独满足：

- 至少 3 个授权、脱敏、包含成熟结果的真实案例；
- 案例覆盖至少两个不同平台、市场、生命周期或失败/退出类型；
- 输入、模型版本、参数版本、输出和实际结果均有哈希；
- 有基线或反事实，能够解释偏差和替代原因；
- 有校准、漂移、事故、回滚及残余风险记录；
- 由非实现者完成独立复核；
- 重大财务、法律、税务、隐私、安全或外部写入仍由适格责任人批准。

系统级 production-ready 还要求所有关键路径上的域均达到 L4；非关键 planned 域必须
fail closed，并证明不会被运行时错误调用。

## 8. 问题分级与整改闭环

| 等级 | 定义 | 时限与处理 |
|---|---|---|
| P0 | 安全、证据造假、主权越权、资金/合规红线或不可逆错误 | 立即阻断发布 |
| P1 | 核心合同、复算、血缘、安装、关键场景或回滚失效 | 修复并复验后发布 |
| P2 | 专业深度、证据覆盖、路由、文档一致性或可维护性不足 | 纳入当前发布整改 |
| P3 | 不影响结论的表达、导航或体验改进 | 排期处理 |
| External Gate | 需要真实授权数据、独立签署或外部平台 | 保持受控关闭，不伪造完成 |

整改项必须有唯一 ID、证据、owner、目标日期、影响路径、复验方式和状态。状态只允许
`open`、`in_progress`、`fixed_reverified`、`accepted_risk`、
`controlled_external_gate`；不得仅写“已优化”。

## 9. 审计报告固定结构

1. 审计对象与不可变快照
2. 范围、排除项和方法
3. 总体判定、总分、硬门结果和成熟度
4. 评分明细与扣分证据
5. L1—L4 分层结论
6. 逐域专业深度
7. 跨域主权、合同和血缘
8. 场景、对抗、容量和恢复
9. 安全、发布与供应链
10. 证据台账和原始日志索引
11. P0—P3、External Gate 整改台账
12. 局限、独立复核和最终签署

## 10. “100 分”验收定义

只有同时满足以下条件，审计对象才可获得 100 分：

1. 九个评分维度均取得满分；
2. G0—G5 全部通过；
3. 没有 open P0/P1/P2；
4. External Gate 已以真实证据关闭，不是被豁免或移出范围；
5. 审计产物、原始日志与被审计 commit 可复现；
6. 独立复核者确认结论与证据一致；
7. 本地 `main`、`origin/main` 和远端 `refs/heads/main` 指向同一已审计提交。

在 L4 尚未关闭时，可以做到“审计报告规范完整度 100%”，但系统成熟度不得记为
100 分或 production-ready。这一区分是本标准不可放宽的可信度底线。

## 11. 权威自动化入口

- `scripts/generate_system_audit_evidence.py`：生成不可覆盖的证据包、日志、哈希、
  测试总账、容量结果、安全检查和变更影响闭包。
- `scripts/score_system_audit.py`：按本标准计算九维分数与G0—G5，不允许工作区、
  独立复核或L4状态被文字覆盖。
- `scripts/validate_release_compliance.py`：验证许可证声明与隐私合同边界，但明确不替代
  法律意见、授权责任人或外部分发批准。

自动生成结果优先于人工汇总；人工报告与机器分数冲突时，必须先修复证据或评分器，
不得手工把分数调高。

## 12. 专业工程门与 L4 分离

当审计范围明确排除 L4 时，只允许使用 `controlled_pilot_engineering_ready` 描述 L1—L3 工程结论，并运行 `scripts/validate_release_integrity.py`。该门必须覆盖十三个当前域的源案例指纹、Golden 差异、证据—主张—根因—动作关系、数值复算入口、跨域主权、状态连续性和防篡改突变。

排除 L4 不等于通过 L4，也不改变本标准第 7、10 节对 production-ready 的要求。报告必须在同一结论区单列 `L4_EXTERNAL_ASSURANCE=SEPARATE_NOT_PASSED`，不得将其作为 L1—L3 工程失败，也不得省略。
